# 权限进度汇报改稿设计

**日期：** 2026-08-24

## 目标

把 `story/agent-safety-gap-analysis-20260819.html` 从“8 月 19 日的缺口分析”更新为可直接用于管理汇报的版本：先解释权限层要解决什么，再说明当前代码走到哪里、哪些已经实测、哪些仍不能按生产可用汇报。

## 汇报口径

所有进度只使用三种状态：

1. **已实现并实测**：主链路已有代码，并有与该结论匹配的测试或真实协议运行证据。
2. **已实现待真机闭环**：代码和非 live 测试已完成，但正式配置、真实回调、真实设备或生产环境闭环尚未验证。
3. **尚未实现**：目标能力仍缺少统一机制或端到端闭环。

不把“有接口”“有代码”“局部测试通过”写成“已经上线”。

## 页面结构

保留原报告的 15 条需求和参考方案分析，在需求索引前新增“截至 2026-08-24 的权限进度”章节，并同步修正文中已经过时的状态。

新增章节按领导首次接触项目的阅读顺序组织：

1. 一句话结论：权限底座和人工确认主链已形成，但离“按任务边界和风险自动分四档”仍有距离。
2. 权限判断链：身份/能力 → 硬拒绝 → 运行模式 → 人工确认 → 资源租约与执行 → 审计。
3. 三档进度表：已实现并实测、已实现待真机闭环、尚未实现。
4. 关键边界：Web 已完成真实协议审批闭环；CLI 已实现本地确认；飞书代码已接通但正式 principal 的 `tool.auto` 会绕过确认，真实 callback 身份闭环和批准后 exactly-once 仍未验证；设备能力、租约和急停仍缺真机 gate。

## 需要同步修正的旧结论

- 将“确认接口全系统无实现”改为当前事实，并区分 CLI、Web、飞书成熟度。
- 将“权限只有只读/写两档”改为：底座已经加入 principal capability、模式、硬拒绝和确认，但尚未形成面向运维语义的自动/确认/补参/接管四档分类器。
- 将“0 条完全达标”改成不会误导的阶段性结论，避免用一个总数字掩盖“底座已完成、业务闭环未完成”的差异。
- 在需求 01、02、03、04、05、08、13、15 和结论/路线图中更新当前进度；其余需求仍保持目标态缺口分析。
