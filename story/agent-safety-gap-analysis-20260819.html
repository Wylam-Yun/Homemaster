安全需求阻断点分析 · CLOUD OPS AGENT

云运维 Agent 安全需求：现状、阻断点与参考方案

Homemaster 在变更场景中要整段接下配合人的工作：按 SOP 做变更前检查、查平台查日志、执行 Linux 命令、核对实例状态、执行后验证、回填结果--人只退到关键节点做审核。这串动作混着完全不同的风险等级。本报告对照 15 条安全需求逐条核对系统现状，并给出可参考的开源方案（微软 AGT 治理工具箱、YoloFS 文件系统）。

15 条安全需求：执行安全 8 条 + 演化安全 7 条，每条独占一页
0 条完全达标尚无一条需求的所有控制点齐备
6 条部分具备止损 / 结果验证 / 审计 / 记忆受控 / 规则受控 / 版本
9 个可借模块来自 AGT 与 YoloFS，逐条对应到需求
权限层要解决的不是传统的"这个用户有没有某个按钮权限"，而是：配合人那串运维动作里，哪些可以安全交给 Agent 自动做，哪些要人确认，哪些要人补信息，哪些必须由人接管。

权限层的真实命题Agent 打满全场之后，"查个日志"和"重启生产服务"会经过同一双手，而人只在四个节点审核。权限层必须在人看不到的地方把风险分开：哪些 Agent 直接做、哪些等人工确认、哪些等人工补参、哪些移交人工执行--这正是后面 15 条需求要补的东西。
02 · Risk Ladder

配合人的动作应分成四档管

同一串运维动作，风险从"基本无害"到"可能造成生产事故"。理想控制是按档位放行；下面每张卡片同时标出：这一档，Homemaster 现在管得住吗。

自动执行

风险低 · Agent 自己做

如 ps -ef | grep java、查日志、看监控--基本无风险。

现状：做不到精准放行权限只有"只读 / 会改动"两档。这类命令要么和重启命令一起被拒，要么一起放开--查日志和 service restart 在权限眼里是同一件事。

人工确认

风险中 · 人批准后执行

如"确认是否执行这个脚本"--有一定风险，应当经人工确认。

现状：确认环节名存实亡框架预留了确认接口，但全系统没有任何一处真正实现"发出确认请求、等待人工批准"。Agent 发不出请求，人也收不到。

人工补参

信息缺口 · 人来补信息

如"需要操作哪个实例？"--Agent 不应该自行推断，应由人补充参数。

现状：没有补参通道参数只验"格式对不对"，不验"值哪来的"。SOP 写"重启对应实例"但没写实例名时，Agent 现在可以自行选择一个。

人工接管

风险高 · 移交人工执行

如 service sshd restart、生产配置修改、删除、回退--风险高，应移交人工。

现状：没有"移交"状态任务只有继续或终止两种，没有"带着上下文暂停、移交人类操作员"的交接机制。

需求01/ 15 · 执行安全

任务边界控制

需求：本次任务只允许执行变更单范围内的事项，越界动作在执行前被拦截。

缺失P0
已有

任务快照（TaskSnapshot）记录目标、子步骤与约束；变更单技能可将票据拆解为步骤和验收标准。

断在

约束字段对权限层不可见：权限判定只读取工具名、读写属性、能力集与路径规则，不接收任务上下文。约束仅作为提示注入模型，属于软约束，模型可以不遵守。

AGTPolicy Engine 执行前拦截（govern / pre_tool）agent-mesh · governance

在 AGT 中，所有工具调用都经过 govern() 包装器进入策略引擎，在 pre_tool 阶段（注：工具实际执行前的检查点）评估 PolicyRule 列表。每条 PolicyRule 是"条件表达式 → 决策"的形式：条件可引用任务上下文、目标资源与参数；决策为 allow / deny / require_approval / warn / log。多条规则结论冲突时按冲突策略合并，默认 deny_overrides（注：存在任一拒绝结论即整体拒绝）。策略表达式求值失败时按拒绝处理，即 fail-closed（故障关闭，宁可误拒不可误放行）。

工具调用请求pre_tool 阶段策略评估（可读取任务上下文）allow / deny / require_approval求值异常 → 按 deny 处理
落地

为 Homemaster 权限判定增加"任务上下文"输入：运行开始时从变更单 + SOP + 当前步骤派生允许动作清单，作为硬约束参与每次工具调用的判定；判定逻辑异常时按拒绝处理。

需求02/ 15 · 执行安全

操作对象控制

需求：只能操作变更单中声明的机器和实例；目标不在范围内或存在歧义时，动作不得执行。

缺失P0
已有

设备租约（device lease，注：带世代校验的设备独占授权）限定只能操作本任务申领的设备；浏览器模式限定每个任务可访问的站点。

断在

命令执行与外部系统调用的目标参数完全由模型生成，权限判定不包含"目标是否在变更单声明范围内"这一维度；命令正确但目标实例选错时权限层无感知，同名实例等歧义场景也没有"无法确定即停止"的机制。

AGT策略条件引用目标（action.target）YoloFS资源级规则（Progressive Permission）governance / permissions

AGT 的策略条件可以直接引用本次动作的 target 与 arguments，因此"目标不在允许清单内"本身就可以写成一条规则。YoloFS 的做法更进一步：权限规则挂在具体路径（资源）上而非工具类别上，每个路径有独立状态（allow / write-ask / read-only / ask / deny，默认 ask）--"可以使用 shell"与"可以在某台生产机上使用 shell"是两条独立的规则。

动作 + 操作目标比对变更单资源清单在清单内 → 继续后续判定不在清单 / 存在多个候选 → 拒绝并转人工补参
落地

把变更单声明的机器 / 实例清单注入权限判定材料；目标不在清单即拒绝；存在多个匹配候选时不自动选择，转入人工补参流程（见需求 03）。

需求03/ 15 · 执行安全

参数可信控制

需求：关键参数要么来自票据 / SOP，要么由人工补充；模型自行推断生成的参数不得直接用于执行。

缺失P1
已有

每个工具的参数有格式校验（schema 校验，类型不符直接拒绝）；记忆写入有证据门。

断在

校验只覆盖格式、不覆盖来源：无法区分"SOP 写明的实例名"与"模型推断生成的实例名"；参数缺失时没有挂起等待人工补充的通道，Agent 会自行选择一个。

YoloFSask 状态：挂起等待授权（timeout = deny）自建参数来源标注permissions

YoloFS 中路径处于 ask 状态时，访问线程挂起等待用户态授权服务应答，超时未应答按拒绝处理（timeout = deny）。这一"挂起 → 人工应答 → 超时拒绝"的交互模型，正是人工补参所需的运行时语义。在此基础上 Homemaster 自建参数来源标注：为关键参数（实例名、路径、数值）记录来源与可信级别。

关键参数缺失 / 低可信调用挂起，发出补参请求人工补充 → 继续执行超时未应答 → 拒绝执行
落地

票据 / SOP 来源的参数视为可信，模型推断的为低可信；低可信或缺失时挂起转人工补参。（原需求表提到的 ArbiterOS 本机无代码，未核实，不纳入方案。）

需求04/ 15 · 执行安全

风险分级与人工介入

需求：查询类自动执行、确认类经人工批准、缺信息由人工补充、高危动作移交人工执行--四档分开管理。

缺失P0
已有

按身份授予能力集（读设备 / 控设备 / 调外部系统 / 改配置互相独立）；计划模式仅允许只读动作；未经核实的"只读"声明一律从严处理。

断在

权限维度只有"只读 / 写"两档；执行器预留的确认接口（confirmation_handler）全系统无任何实现，人工确认与人工接管两条通道不存在，实际只剩"全自动执行"与"一律拒绝"两个极端。

AGTActionClassifier 动作定级 + Approval 审批hypervisor/rings · approval

AGT 的 ActionClassifier 是纯函数（注：无状态、不调用模型的确定性计算），仅依据动作属性定级：只读 → Ring 3；存在撤销接口（可逆）→ Ring 2；破坏性 → Ring 1；配置 / 管理类 → Ring 0（注：Ring 0–3 为 AGT 的执行环等级，0 最高权限）。策略判为 require_approval 时，系统生成 ApprovalRequest（动作 + 目标 + 参数 + 理由）交由 ApprovalHandler 处理，答复渠道可插拔（控制台 / 回调 / Webhook）。两条设计约束：审批与具体参数绑定，参数变更即审批失效；超时一律按拒绝处理，绝不超时自动放行。

动作提交ActionClassifier 按属性定级只读 → 自动执行可逆 → 发审批请求破坏性 → 移交人工
落地

定级器接在 Homemaster 权限门输出端，四档（自动 / 确认 / 补参 / 接管）映射不同处理；confirmation_handler 按 ApprovalHandler 接口实现，飞书消息审批作为一个回调实现。

需求05/ 15 · 执行安全

异常止损

需求：出现异常时自动停止并阻断后续执行，同时升级人工处理；系统不得自行恢复。

部分具备P0
已有

连续工具调用失败达上限（5 次）自动停止；协议违规与观察失败各有计数上限；命令超时控制；急停后后续动作在执行前被拦截；被中断动作返回"结果未知"且禁止自动重试。

断在

异常停止后仅记录错误日志，不产生任何人工通知；守卫指标只有失败计数，缺少调用速率、越权尝试等行为维度指标，也没有"停止后升级人工处理"的路径。

AGTRingBreachDetector + Circuit Breaker（行为违规检测与熔断）hypervisor/rings

AGT 的 agent-hypervisor 内置 RingBreachDetector（环违规检测器），在滑动时间窗（注：只统计最近 N 秒、不断向前滑动的观察窗口）内持续计算两类指标：①工具调用速率相对历史基线的倍数，倍率 2 / 5 / 10 / 20 倍分别对应 LOW / MEDIUM / HIGH / CRITICAL 四级；②越权尝试（privilege escalation）累计权重--Agent 尝试访问高于其执行环等级的资源时，等级差越大计分越高。任一指标达到 HIGH / CRITICAL 即触发 Circuit Breaker（熔断）：系统拒绝该 Agent 的全部后续工具调用；熔断状态不会自动恢复，必须由管理员显式重置。

滑动窗口内统计：调用速率 + 越权计分按基线倍率分级（LOW / MEDIUM / HIGH / CRITICAL）HIGH / CRITICAL -> 触发熔断，拒绝一切调用等待管理员显式重置
落地

接入 Homemaster 运行时现有守卫处，把"仅失败计数"升级为"失败计数 + 速率异常 + 越权尝试"三指标；熔断与异常停止均通过通知通道（本地 / 飞书）升级人工处理，人工处置前不允许恢复执行。

需求06/ 15 · 执行安全

执行结果验证

需求：任何写操作完成后，必须经独立通道核实外部世界真实状态，才能判定任务完成。

部分具备已有优势
已有

急停要求"控制回执 + 独立状态查询"双证据齐备才判定成功；浏览器每步写操作强制截图回传核对；Hawkeye（检查旁挂系统）提供证据核验。

断在

双证据机制只覆盖急停与浏览器两处；命令与外部系统调用以返回码判定完成，"服务是否启动、日志是否报错"的复核是模型可选项，不是制度。

自建双证据范式制度化（自家急停 / Hawkeye 范式推广）

以急停双证据为模板：控制通道返回成功只是必要条件，必须由独立观测通道（状态查询 / 日志 / 监控）确认外部世界终态，两者一致才判定完成。这一判据在 Homemaster 内部已有三处实现（急停、浏览器截图、Hawkeye），做法是把它推广为所有写操作的统一完成标准，无需外部参考。

写操作执行控制通道返回码独立状态查询（进程 / 日志 / 监控）两证据一致 -> 判定完成
落地

在任务完成判定处强制插入独立验证步骤，复核结果与预期一致才允许标记任务成功；Hawkeye 作为核验执行器接入。

需求07/ 15 · 执行安全

回退管理

需求：高风险操作前保存现场快照并预声明回退方案；出问题时能恢复到操作前状态。

缺失P0
已有

无。

断在

操作前无现场保存；高风险动作放行前不检查回退方案是否就绪；执行人要求回退时，Agent 提供不了操作前状态与回退参数。

YoloFSSnapshot 快照AGTSagaOrchestrator 分步补偿snapshot · saga

YoloFS 在每条命令执行完成后自动创建快照，快照构成可回溯的时间线，支持恢复至任意一代。AGT 的 SagaOrchestrator（注：Saga 是分布式系统里"长事务拆成带补偿的短步骤"的模式）要求多步操作的每一步在启动前声明补偿动作；任一步失败时，对已完成的步骤按逆序执行补偿；补偿失败的步骤如实列入失败清单上报，不伪装成"已完全回滚"。

操作前自动创建快照多步执行，每步预声明补偿动作失败 -> 逆序执行补偿补偿失败 -> 如实上报失败清单
落地

权限门放行高风险动作前检查两个前置条件：现场快照已创建、每步补偿动作已声明；回退执行按 Saga 逆序补偿。

需求08/ 15 · 执行安全

全过程审计

需求：每一步都记录"做了什么、依据什么、经谁授权"，事后可还原完整决策链，且记录不可篡改。

部分具备P0
已有

每次运行有完整 JSONL 事件流水；设备、急停、外部调用有独立审计链；会话结束有归档工序。

断在

记录了"做了什么"，缺少"依据与授权"字段：决策依据（哪张变更单哪一步）、参数来源、审批人不是独立字段；记录之间没有以变更单为键的关联索引。

AGTMerkleAuditChain 防篡改审计链audit

AGT 的审计链是 append-only（仅追加、不可修改）+ 哈希链结构：每条记录包含上一条记录的哈希（注：哈希是数据的数字指纹，内容任何一点改动都会使指纹变化），事后篡改任意一条，其后所有指纹校验都会失败。每条决策记录固定携带三个字段：arguments_hash（参数指纹）、approver_did（审批人标识）、policy_version（当时生效的策略版本），使"批的就是这组参数、批的人是谁、按哪版规则"事后均可核对。

决策发生追加记录：参数指纹 + 审批人 + 策略版本记录含上一条哈希，首尾成链篡改任意一条 -> 后续校验失败
落地

在现有 JSONL 流水中增加参数指纹、审批人、策略版本、变更单键四个字段，并按变更单 ID 建立跨记录索引；归档工序增加链式校验。

04 · Evolution Safety

演化安全（需求 9–15）：以后不能越学越错

Homemaster 的学习通道是自动的：会话结束总结经验、定期记忆整理（系统内称 dreaming）、可创建技能候选。但"审核后再生效"的流水线，六段里只有第一段存在。YoloFS 的 Staging-Commit 范式恰好补的是后面五段。

已有

生成

自动沉淀经验、定期整理记忆、创建技能候选，生成侧通道齐全。

缺失

候选区

新知识应先进隔离区验证；现在是写入直接进正式库。

缺失

验证

应有测试集 / 真实轨迹回放、新旧对比；现在没有任何验证环节。

缺失

审批

生成权和发布权应分离；现在谁生成谁生效。

缺失

发布与版本

应有版本、差异、回滚；现在新版替换就是覆写文件。

缺失

生效确认

应确认 Agent 实际加载了新版；现在"后台换新、前台用旧"无法被发现。

唯一正样本：插件机制外来插件必须经部署者预先批准、锁定指纹、核对版本、权限取交集--这正是"生成权与发布权分离"的完整实现，但只对插件生效，没有推广到知识、记忆和技能。
最大的缺口：直接改文件技能文件和人格 / 偏好文件就是普通文件，禁改清单只覆盖了凭据类路径。模型一旦有写文件权限，可以直接修改自己的正式知识和技能，绕过记忆系统里的证据门。YoloFS 的暂存区机制正对此。
需求09/ 15 · 演化安全

知识修改受控

需求：新知识先进候选区验证，经人工审核后才生效；正式知识库对 Agent 只读。

缺失P0
已有

记忆有类型体系（事实 / 经验 / 技能候选 / 文件知识）；写入正式库前有证据门。

断在

写入直接进入正式检索库，没有候选隔离区；更大的缺口是技能与知识文件是普通文件，模型具备写权限时可直接修改正式内容，绕过证据门。

YoloFSStaging-Commit（先暂存、审核后提交）staging

YoloFS 将 Agent 的全部写操作重定向到 .yolofs/inodes 暂存区并记入仅追加日志，正式内容在 commit 之前不变更；人工通过 review 查看变更清单与逐行差异后，执行 commit 使变更生效，或执行 abort 丢弃全部暂存（abort 为 O(1) 操作，即时完成）。整个机制由文件系统层强制，Agent 无法绕过。

Agent 发起写入重定向至暂存区，正式内容不变人工 review 变更清单与差异commit 生效abort 丢弃
落地

知识库写入路径改为"暂存 -> 人工审核 -> 提交"；正式知识库对 Agent 设为只读，禁改清单覆盖知识文件。一个机制同时补上"没有候选区"和"直接改文件"两个缺口。

需求10/ 15 · 演化安全

Memory 修改受控

需求：记忆的修改与删除须标注来源和可信级别；自动整理通道的产出同样须经人工审核后入库。

部分具备P1
已有

新增记忆有证据门；单条记忆有版本链（当前版 / 归档版可查）；纠错仅限本轮真实读取过的记忆；有敏感内容过滤。

断在

修改与删除不强制标注来源与可信级别；会话结束自动反馈与定期记忆整理两条自动通道的产出直接落库、无人工审核--一次推断可能固化为长期事实。

YoloFSStaging（自动产出进暂存）自建来源与可信级别标注staging

与需求 09 同一套 Staging-Commit 机制，应用对象换成自动生成的记忆：自动通道的产出同样先入暂存区，经人工审核后提交入库。同时自建来源元数据：每条记忆标注"来源 + 事实 / 推测"（票据 / SOP 检索所得 = 事实，模型推断 = 推测），推测类记忆不得作为事实长期保留。

自动总结 / 定期整理产出写入暂存区（不直接落库）人工审核提交入库，标注来源与可信级别
落地

记忆写入管道在证据门之后增加暂存与审核环节；两条自动通道不再直接写正式库。

需求11/ 15 · 演化安全

规则修改受控

需求：约束 Agent 行为的一切规则--权限配置、技能正文、人格设定--Agent 均无权修改。

部分具备P0
已有

权限规则存放于受保护配置（仅管理员可读、不入版本库），修改需独立能力，配置路径在禁改清单；提示词、技能、附件无扩权能力。

断在

约束 Agent 行为的不只有配置文件--技能正文与 SOUL / USER 人格文件同样是事实上的行为规则，而它们可被模型直接写改：约束本身可以从旁边被解除。

AGT策略即数据（Policy as Data）YoloFSStagingpolicy

AGT 中策略是带版本号的数据文件，策略变更与代码变更同等对待、走发布流程，Agent 无权修改生效中的策略。YoloFS 则在文件系统层保证正式内容的提交权仅属于人。两者结合：规则文件的修改统一走"候选 -> 审核 -> 发布"，Agent 至多起草候选规则。

规则需要修改Agent 仅可起草候选规则人工审核差异发布新版本，生效规则对 Agent 只读
落地

把技能正文、SOUL / USER 人格文件、权限配置全部纳入"事实规则"清单，统一走候选发布流程，并加入文件禁改清单。

需求12/ 15 · 演化安全

Skill 演化受控

需求：新技能先经评测证明优于旧版，再经人工批准后才替换正式技能；旧版保留可回退。

缺失P0
已有

具备技能创建能力；记忆类型中有"技能候选"；技能加载有来源优先级。

断在

技能候选没有任何机制转化为可用技能；技能定义（SkillDefinition）没有版本字段，技能更新即覆写文件，无从对比新旧效果。

YoloFSStaging + Snapshot Timeline（候选-评测-提交完整链条）staging · timeline

候选技能写入独立候选目录（对应暂存区）；以同一批历史任务分别运行新旧版本并对比结果（对应 YoloFS 的快照间 diff，注：YoloFS 支持查看任意两个快照之间的差异）；人工审核通过后才替换正式技能（对应 commit），替换前旧版本始终可用，且每次替换自动形成新的快照点，可随时回退。

新技能写入候选目录历史任务集上新旧对比评测人工审核替换生效，旧版本保留可回退
落地

为 SkillDefinition 增加版本字段；建立候选目录与评测流程，技能替换统一走发布通道（见需求 13）。

需求13/ 15 · 演化安全

人工审核与发布

需求：生成的主体（Agent）与发布的主体（人）必须分离；任何资产的生效须人工批准。

缺失P0
已有

插件机制完整实现"部署者预先批准 + 指纹锁定 + 版本核对 + 权限取交集"的发布管控。

断在

该管控仅覆盖插件；技能、记忆、知识没有任何审批发布环节，用户技能目录写入即生效。

YoloFS提交权分离（commit 仅限人工）staging

YoloFS 的设计中，Agent 对文件可读、可回溯历史，但 commit（提交）动作只能由人在用户态显式执行，文件系统层不提供任何 Agent 提交路径--生成权与发布权在系统层即被分离，不依赖 Agent 自觉。

Agent 生成候选内容人工 review 差异人工执行 commit，变更生效Agent 无提交路径（系统层强制）
落地

把插件机制已有的"批准 + 指纹 + 版本"验核推广到技能、记忆、知识全部资产；提交动作仅保留在人工接口。

需求14/ 15 · 演化安全

版本与回滚

需求：每次变更有版本号、可查差异、可整体回滚到上一个稳定版本。

部分具备P1
已有

单条记忆有版本链；插件有版本锁定。

断在

技能无版本、无差异记录；记忆只有逐条历史，缺少"整体恢复到上一个稳定集合"的能力--自动整理批量产出问题记忆时，逐条回滚不可行。

YoloFSSnapshot / Timeline / Travel（快照时间线）snapshot · timeline

YoloFS 的快照构成有向无环图（DAG）时间线：支持 travel（恢复）至任意一代、查看任意两代之间的差异、以及单文件的完整变更历史。每次发布即一个快照点，回滚是"整体恢复至某一代"，而不是逐条撤销。

每次发布自动创建快照快照构成时间线异常时 travel 回上一稳定代任意两代间可查差异
落地

知识与技能库以"发布代"为版本单位建快照；记忆库增加"稳定集合点"标记，自动整理执行前必须先创建快照点。

需求15/ 15 · 演化安全

生效验证

需求：发布后确认运行中的 Agent 实际加载了新版本；版本不一致时告警并阻断。

缺失P0 · 需自建
已有

体检命令可静态列出本次将加载的技能与模型。

断在

只有发布前检查，没有发布后闭环--"后台已更新、运行中 Agent 仍使用旧版本"无法被发现。

自建发布后版本核对闭环AGTpolicy_version 字段作积木audit

AGT 每条决策审计记录携带 policy_version（当时生效的策略版本），使"任意时刻实际生效的版本"可追溯、可核对。两个开源项目都没有完整的发布后确认机制，这部分需自建：以上报与比对构建闭环--运行中的 Agent 定期上报实际加载的技能 / 规则版本，与发布记录自动比对，不一致即告警并视为发布未完成。

发布完成，记录目标版本运行中 Agent 上报实际加载版本自动比对不一致 -> 告警并阻断
落地

为技能与规则增加运行时版本上报接口，纳入审计流水；比对失败视为发布未完成，阻断相关能力使用。

05 · Reference

两个开源项目：能借什么、怎么借

前面 15 页里反复出现的模块，在这里集中说明。先讲清两个项目是什么、跟我们的关系，再逐个讲模块--每个模块按"是什么 / 怎么运作 / 借来做什么"三行。

AGT 治理工具箱

微软开源 · Python 库
是什么

一套给 AI Agent 加装"策略管控与决策审计"的工具箱：任何工具调用先经过配置好的规则，被拒的动作在代码层就无法发出。

核心思路

不依赖模型自觉（提示词不是控制手段），在确定性代码中拦截--"被拒绝"不是"大概率不执行"，是"结构上无法执行"。

怎么借

它和 Homemaster 已有的权限门是同一层组件，直接叠加安装会导致两道判定互相冲突。所以借的是设计（拦截 / 审批 / 熔断 / 审计字段），实现进我们自己的权限门。

YoloFS 文件系统

开源 · Linux 文件系统 + 命令行
是什么

一个专门管控 AI Agent 文件写入的文件系统：Agent 的一切写操作先落在暂存区，正式文件在人工审核之前不变更。

核心思路

把"信息"（它到底改了什么）和"控制"（改不改得成）从 Agent 手里移到系统层，不依赖 Agent 自觉。

怎么借

它只管本机文件、不管远程服务，且是内核模块（生产环境适用性需另行评估）。所以借的是机制范式（暂存 / 快照 / 先问后写），落在我们自己的技能 / 知识 / 配置管理层。

执行前拦截

AGT · Governance Gate / Policy Engine
是什么

所有工具调用先经过配置好的规则，再决定放行 / 拒绝 / 转人工审批。

怎么运作

规则是"条件 -> 决策"：条件可引用"这次是什么任务、操作什么对象、带什么参数"，如"目标环境是生产且动作是删除 -> 拒绝"。一条纪律：规则求值失败按拒绝处理--宁可误拒，不可误放。

借来做什么

需求 01 / 02 的载体：把变更单、SOP 步骤、对象清单放进规则判断材料，"越界"从提示语变成硬约束。

审批通道

AGT · Approval
是什么

规则判"此事需人工批准"时，系统生成审批请求（动作 + 目标 + 参数 + 理由），发送给人，等待答复。

怎么运作

两条约束：①审批绑定具体参数，参数变更即审批失效、须重新申请；②超时未答复一律按拒绝处理，绝不超时自动放行。答复渠道可插拔：控制台、外部回调均可（接飞书消息就是实现一个回调）。

借来做什么

需求 04 / 05 的人工确认 + 人工补参：Homemaster 权限门预留了确认接口但没有实现，这套接口设计直接采用。

动作定级器

AGT · ActionClassifier
是什么

给每个动作自动评定风险等级的纯规则计算器。

怎么运作

只看动作自身属性：是否只读？是否有撤销接口（可逆）？是否破坏性？是否配置 / 管理类？--输出"风险档 + 可逆性"。纯函数计算，不经过模型，不靠模型自评。

借来做什么

需求 04 的判定内核：查询 / 修改 / 重启 / 删除四档分级由它算出，每档接一种处理（自动 / 确认 / 补参 / 接管）。

熔断器

AGT · Breach Detector / Circuit Breaker
是什么

行为违规检测与熔断：检测到高危异常后，拒绝该 Agent 的全部后续调用。

怎么运作

在滑动时间窗内监测两类指标：调用速率相对基线的倍数（2/5/10/20 倍对应四级告警）；越权尝试累计权重，执行环等级差越大计分越高。达到 HIGH / CRITICAL 即触发熔断，且必须由管理员显式重置，系统不自动恢复。

借来做什么

需求 05 止损：Homemaster 已有"连续失败 N 次即停"，缺的正是行为维度指标（速率 / 越权）和"熔断后须人工重置"。

分步补偿

AGT · Saga
是什么

多步操作的回滚机制：每一步预先声明自己的补偿（撤销）动作。

怎么运作

步骤按顺序执行；任一步失败时，已完成的步骤按逆序执行各自补偿动作；补偿失败的步骤如实列入失败清单上报，不包装成"已全部回滚"。

借来做什么

需求 07 的多步回退：变更操作常是多步串行，每步带补偿声明，失败自动逆序回滚。

防篡改审计

AGT · MerkleAuditChain
是什么

仅可追加、不可篡改的决策记录链。

怎么运作

每条记录包含上一条记录的哈希，首尾相连--事后修改任何一条，其后所有指纹校验都会失败。记录内容包含：参数指纹、审批人、当时生效的策略版本。

借来做什么

需求 08 的审计字段与防篡改设计；"策略版本"字段同时是需求 15 的积木。

暂存区

YoloFS · Staging
是什么

Agent 全部写操作的缓冲机制：先写入隔离暂存区，正式内容不变更。

怎么运作

写操作全部重定向到隐藏的暂存目录并记入仅追加日志；人工用 review 查看变更清单和逐行差异，执行 commit 才真正生效，执行 abort 一键全部丢弃。全程文件系统层强制，Agent 无法绕过。

借来做什么

需求 07 / 09 / 12 / 13 的候选区：技能、知识、记忆、配置的修改一律"暂存 -> 人工审核 -> 提交"，正式库对 Agent 只读。

快照时间线

YoloFS · Snapshot / Timeline / Travel
是什么

"检查点"体系：每条命令执行完自动创建快照，可随时恢复至任意一代。

怎么运作

快照构成有向无环图时间线；支持恢复（travel）至任意一代、查看任意两代之间的差异、查询单个文件的完整变更历史。

借来做什么

需求 07 的"操作前保存现场" + 需求 14 的版本回滚：每次发布即一个快照点，新版异常时回退到上一快照。

渐进权限

YoloFS · Progressive Permission
是什么

文件路径的五档规则：allow / write-ask / read-only / ask / deny，默认 ask（访问前询问）。

怎么运作

遇到"询问"类操作，访问线程挂起等待用户态授权服务应答，超时未应答按拒绝处理。规则无需预先配全：Agent 实际触碰到什么敏感路径，就补充一条对应规则--权限随使用逐步完善，而非一次性配置。

借来做什么

需求 04 在文件维度的落地：Homemaster 的文件权限从"允许 / 拒绝"二值扩展为五档，write-ask 直接对应人工确认档。

两个项目共同的底层纪律：出现任何意外，一律拒绝（fail-closed，故障关闭）规则求值失败 = 拒绝；审批超时 = 拒绝；无应答 = 拒绝；熔断后必须人工重置。宁可误拒、不可误放。建议把这条定为 Homemaster 权限层的第一设计原则，其重要性高于任何单个模块的引入。
06 · Root Blockers

三个横切断点，堵住 15 条里的大半

15 条阻断点不是 15 个独立问题。向上游看，是三个架构级缺口；它们不补，逐条打补丁会被反复绕过。每个断点都标注了对应的参考模块。

01

没有人工确认通道

卡住需求 03 · 04
现状

框架预留了确认接口，但全系统没有任何一处真正实现"发出确认请求、等待人工批准"；本地和远程渠道（飞书）都没有。

后果

四级管控里的中间两档（人工确认、人工补参）无处落地。系统只剩两个极端：全自动，或一律拒绝--前者不敢启用，后者等于不可用。

补法

先做本地交互确认，再做远程（飞书消息审批）；审批绑定具体参数，超时即拒；确认记录落审计。

参考

AGT Approval：审批请求（动作 + 目标 + 参数 + 理由）、参数变更即失效重新申请、超时 = 拒绝、答复渠道可插拔。

02

权限门只认身份、不认任务

卡住需求 01 · 02 · 03
现状

权限按身份预先配置，与"本次任务是什么"完全无关；任务快照上的约束只是给模型看的提示，权限判定不读取。

后果

任务边界、操作对象、参数来源三条需求都没有载体：变更单声明的机器范围进不了权限判断，"本步骤允许哪些动作"无法变成硬约束。

补法

给权限判定增加任务级输入：运行开始时，从变更单 + SOP + 当前步骤派生"允许 / 禁止动作清单"，运行中逐条比对。

参考

AGT Policy Engine：规则条件可引用任务、目标、参数，"越界即拒"是一条配置而非一段提示词；规则求值失败也按拒绝处理。

03

学习只生成、无发布管控

卡住需求 09 · 12 · 13 · 14 · 15
现状

生成侧通道齐全（自动沉淀、定期整理、技能候选），候选区、验证、审批、版本、生效确认五段全缺；且技能文件是普通文件，模型可直接修改。

后果

Agent 学到的任何内容--包括一次误判--都可以直接改变自己后续的行为，没有拦截，也无法回退。

补法

采用插件机制的五段结构：候选区 -> 验证 -> 审批 -> 带版本发布 -> 生效确认；同时把技能 / 人格 / 记忆文件列入禁改清单。

参考

YoloFS Staging + Timeline：暂存 -> 人工审核 -> 提交 / 丢弃的完整范式，提交权仅属于人；每次提交是一个快照点，可回退、可比对。

07 · Roadmap

建设路线：三步走

排序原则：先打通"人"和"任务"进入权限体系的通道（否则一切分级管控无处落地），再推广已有的成熟范式，最后一次性建成演化安全流水线。每项都标注了参考来源。

第一优先

把「人」和「任务」接进权限体系

现在权限只认身份，既不认任务，也没有人工介入的通道。

1 · 实现人工确认通道

先本地、后远程；确认记录落审计。

参考：AGT Approval（超时即拒、绑定参数、飞书可接）

解决需求 03 · 04
2 · 任务级动作清单进权限门

从变更单 + SOP + 当前步骤派生允许 / 禁止清单，作为硬约束。

参考：AGT Policy Engine（规则引用任务上下文）

解决需求 01 · 02
3 · 技能、人格、记忆文件列入禁改清单

一行配置，堵住"模型修改自身规则"最大的缺口。

参考：YoloFS 默认 ask 状态

解决需求 09 · 11
第二优先

把已有的成熟范式推广成制度

范式在代码里已存在，是复制推广而非新开发。

4 · 写操作后强制独立验证

执行后必须独立核实服务状态、日志，才能标记成功。

参考：自家急停双证据 + Hawkeye 证据核验

解决需求 06
5 · 异常停止时升级人工处理

补上止损的"升级人工"环节：带上下文的通知与交接。

参考：AGT Circuit Breaker（熔断后须人工重置）

解决需求 05
6 · 审计补充三个字段

决策依据（哪张变更单哪一步）、参数来源、审批人。

参考：AGT 审计字段（参数指纹 / 审批人 / 策略版本）

解决需求 08
第三优先

演化安全流水线一次成型

五段结构按成熟范式建设。

7 · 候选区 + 审批发布 + 版本回滚 + 生效确认

知识、技能、记忆统一走：生成 -> 候选 -> 验证 -> 审批 -> 发布 -> 生效确认。

参考：YoloFS Staging + Timeline + 提交权分离

解决需求 09 · 12 · 13 · 14 · 15
8 · 回退声明与放行前检查

高风险动作放行前必须声明回退方案；回退执行器待真实环境接入。

参考：YoloFS Snapshot + AGT Saga

解决需求 07 · 10
08 · Outcome

架构基础是健康的，缺口是明确的，参考是现成的

这次分析没有推翻任何现有设计--多数需求的"标准答案"已经存在于系统的某个环节或两个开源项目中，问题在于把它们接入 Homemaster 的权限门并推广成制度。

已经就位 / 有现成参考

  • 所有工具调用经过同一道权限门，按身份授予能力集
  • 设备租约 + 急停"双证据"，是结果验证的成熟范式
  • 连续失败自动停止、命令超时、被中断动作禁止自动重试
  • Hawkeye 证据核验是自家优势，需求 06 无需外部参考
  • 拦截 / 审批 / 熔断 / 审计：AGT 四件套有经源码核实的设计可采用
  • 暂存 / 快照 / 先问后写：YoloFS 三项范式可平移到知识资产层

缺口在哪

  • 权限判定中没有任务、没有人工：不识别变更单范围，也没有确认 / 补参 / 接管通道
  • 风险不分级：ps -ef 和 service restart 同档
  • 异常停止后不升级人工处理；高风险动作执行前不检查回退方案
  • 学习只生成、无发布管控，且技能 / 知识文件可被模型直接修改
  • 审计记录了"做了什么"，拼不出"依据什么、经谁授权"
  • 需求 15（生效验证）两个项目都不够，必须自建
结论

15 条需求，0 条完全达标、6 条部分具备。补齐路径明确：给现有权限门增加"任务"和"人工"两个输入，把急停双证据、插件审批这两个自家范式，连同 AGT 审批、YoloFS 暂存这些现成设计，统一推广成制度。
