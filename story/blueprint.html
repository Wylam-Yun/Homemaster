WHY WE NEED AGENT

双维痛点全景

问题来自两个维度：配合人的工作方式，以及现有作业流程的结构性缺陷。它们共同决定了 Agent 必须解决什么。

① 配合人工作痛点

人力被消耗在等待、切换、整理与重复操作上

1

长期陪跑，有效工作占比低

全程在线但多数时间在等待，一人仅配合一份变更，人力利用率低。

人力浪费
2

多系统切换，信息获取成本高

变更单、运维平台、命令日志、监控系统频繁切换，易遗漏关键内容。

信息分散
3

认知负担重，容易漏检误判

一边理解 SOP、一边记忆进度、一边判断动作，步骤多时易漏看错看。

漏检误判
4

证据整理与结果回填繁琐

事后手工查日志、截图、整理时间、填写结果，精力被消耗在材料上。

事务性负担
5

重复操作降低作业严谨度

大量相同检查动作，长期重复后产生惯性，简化甚至跳过部分步骤。

严谨度下降

② 现有作业流程痛点

流程结构与协作机制本身存在缺陷

1

执行进度依赖人工同步

口头/消息通知易出现「已完成未通知」或「声明完成未核验」。

过程不连续
2

SOP 与真实操作缺少自动对应

「应做什么」与「实际做了什么」需手工逐项比对，步骤越多越易漏项。

核验成本高
3

监督集中在事后，异常发现不及时

执行完成后才统一核验，漏做错做被发现时风险已进入生产。

风险晚发现
4

不同风险任务采用相同协作方式

状态查询与服务重启都需人工介入，缺少差异化协作，低风险过度依赖人工。

协作无差异
5

经验难沉淀、难复用、难保持有效

经验存在个人脑中，相似变更重新理解；缺少验证更新机制，易过时失效。

经验流失
WHAT AGENT MUST DO

Agent 六大核心能力

每一项能力直接对应一组痛点，构成 Agent 必须具备的能力底座。能力 ⑥（经验自进化）是本次改造的核心重点。

1

完整作业流程理解能力

自动解析变更单和 SOP，识别变更前检查、过程监督、结果验证、异常停止与回退要求，把自然语言转化为可执行步骤与核验标准。

痛点 3SOP 拆解核验标准
2

低风险任务自主执行能力

自动完成状态查询、日志检索、监控检查等标准化低风险工作，让配合人只在关键节点和异常情况介入。

痛点 1·2·5减少重复
3

基于真实证据的持续核验能力

持续获取命令记录、平台操作和系统状态，对照 SOP 判断动作是否执行、对象参数是否正确、结果是否达标，异常时及时提醒与中断。

痛点 6·7·8多源证据
4

分级人机协作能力

低风险自动执行；一定风险请求 Yes/No 确认；缺参数只补必要信息；高风险/不可逆操作携带完整上下文移交人工。

痛点 9L1-L4不越权
5

过程管理与审计能力

自动跟踪进度、已完成动作、证据、风险状态与待办，支持多变更并发；异常主动通知，结束自动整理证据、回填结果、生成审计报告。

痛点 1·4·6·8多变更并发
6

经验沉淀与持续迭代能力

将检查方法、判断依据、异常处理与成功轨迹沉淀为可复用经验，并随 SOP、环境、执行结果持续验证、修正与淘汰，保证经验始终准确可靠。

痛点 5·10本次重点 ★
CURRENT STATE & GAPS

现有能力 vs 能力缺口

现有 Agent 框架已具备 10 项基础能力，但要支撑运维变更协作场景，仍有 8 项关键缺口需要补齐。点击任一项可查看详情。

✓

自主规划执行

理解目标、拆解子任务、持续调用工具推进

能够理解用户的最终目标，自动拆解为可执行的子任务，并持续调用工具推进任务直到完成，无需逐步指令。

✓

工具调用执行

调用本地/环境/MCP 外部工具真正执行操作

支持调用本地工具、环境工具以及 MCP 外部工具，能够真正对外部系统执行操作，而非仅生成文本。

✓

环境观察验证

获取状态并在操作后再次观察判断是否生效

能够获取当前环境状态，并在执行操作后再次观察，判断操作是否真正生效，形成「执行-观察-判断」闭环。

✓

长期记忆

记住用户习惯、环境事实与历史操作经验

能够记住用户习惯、环境事实和历史操作经验，并在后续任务中主动检索复用，而非每次从零开始。

✓

长任务状态管理

记录进度、当前步骤、下一步与执行证据

持续记录任务进度、当前步骤、下一步计划和执行证据，避免长任务中途「失忆」或状态丢失。

✓

长上下文管理

自动压缩冗余历史，保留真正重要的上下文

能够自动压缩冗余历史信息，在长时间、多轮执行过程中保留真正重要的上下文，避免上下文溢出。

✓

权限与安全控制

真实操作统一过权限检查，支持互斥与紧急停止

所有真实操作统一经过权限检查，并支持设备互斥、异常隔离和紧急停止等安全机制。

✓

人机协作

信息缺失/权限不足/需决策时主动询问用户

遇到信息缺失、权限不足或需要人工决策时，可以主动询问用户并在得到回复后继续原任务。

✓

Skill 经验复用

动态加载不同 Skill 复用已有流程与领域经验

能够动态加载不同 Skill，将已有操作流程和领域经验复用到新的任务中，提升一致性与效率。

✓

多端交互能力

通过飞书接收任务、反馈过程与返回结果

已支持通过飞书接收任务、反馈执行过程和返回结果，让用户可以远程与 Agent 持续协作。

!

SOP 理解与任务拆解能力不完整

变更单/SOP 自动转可执行步骤与依赖、成功标准、异常回退

需要把变更单和 SOP 自动转成可执行步骤、依赖关系、成功标准和异常/回退条件，目前还做不到完整覆盖。

!

操作风险判断能力不足

结合动作/工具/目标/参数/影响范围判断风险等级

需要结合动作、工具、目标环境、参数和影响范围，判断一项操作到底属于什么风险等级，目前判断粒度不够。

!

L1-L4 人机协作机制未真正落地

按风险与信息完整度自动选择执行/确认/补参/接管

需要让 Agent 根据风险和信息完整度，自动选择自主执行、Yes/No 确认、补参数或人工接管，分级机制尚未落地。

!

真实运维工具接入还不完整

黑屏命令/白屏平台/监控/工单/配置查询接入执行链路

需要把黑屏命令、白屏平台、监控、工单、配置查询等业务系统真正接入 Agent 的执行链路（已初步支持）。

!

多源证据持续核验能力不足

命令/平台/监控证据持续对齐 SOP，判对象参数顺序结果

需要把命令日志、平台操作、监控状态等证据持续和 SOP 对齐，不只判断「做没做」，还要判断对象、参数、顺序和结果对不对。

!

异常处理与回退闭环不足

发现漏做/错做/异常后判断何时暂停/提醒/回退/接管

发现漏做、错做或环境异常后，Agent 需要知道什么时候暂停、什么时候提醒人、什么时候触发回退或人工接管。

!

过程管理和审计产品化不足

多变更并发/实时进度/主动通知/证据整理/自动回填/审计

需要支持多变更并发跟踪、实时进度展示、主动通知、证据整理、自动回填和最终审计报告。

★

经验沉淀与自迭代能力不足

从轨迹自动总结/验证/更新/淘汰经验，沉淀为可复用能力

目前更多是「记住和召回」，还缺从成功/失败轨迹中自动总结经验、验证经验是否有效、更新或淘汰旧经验，并进一步沉淀成可复用经验。这是本次改造的核心重点。

现有能力是地基，缺口是改造方向，下方将聚焦最关键的缺口 ⑧
DEEP DIVE · GAP #8

聚焦需求 8：经验沉淀与自迭代

这是本次改造的核心。围绕「经验的识别、召回、参与、验证、纠错、固化、约束、追溯」8 个子能力展开。

★ 核心命题：让经验从「记住」进化到「会用、会改、会进化」

经验不能只是被存储和召回，而要真正参与决策、随业务变化自我验证与纠错，并最终固化为稳定能力。每一步修改都可验证、可追溯、可回滚，并由人批准。

REQ 8.1

经验自动识别与沉淀

从执行轨迹自动识别值得复用的内容并结构化沉淀。
Agent 需从每次变更轨迹中自动识别检查方法、操作顺序、关键参数、判断依据、异常处理方式以及成功/失败原因，沉淀为结构化经验，而非依赖人工总结。
展开 ▾
REQ 8.2

经验按场景准确召回

按业务/对象/SOP/环境主动找到相似历史经验。
面对新任务时，Agent 需根据业务类型、操作对象、SOP 步骤和当前环境主动找到相似历史经验，而非简单关键词匹配或把所有历史塞给模型。
展开 ▾
REQ 8.3

经验真正参与当前决策

召回经验要影响规划、工具选择、风险判断与核验。
召回经验不能只是「给 Agent 看」，而要真正影响任务规划、工具选择、风险判断、核验方式和异常处理，例如历史上某类变更易漏某项检查，Agent 应主动补充。
展开 ▾
REQ 8.4

经验有效性验证

结合当前 SOP/环境/执行结果验证经验是否仍有效。
Agent 不能无条件相信历史经验，需结合当前 SOP、生产环境和本次真实执行结果验证经验是否仍然有效，避免因 SOP 更新、工具或环境变化继续使用过期经验。
展开 ▾
REQ 8.5

经验持续更新与纠错

新结果与历史不一致时修正/合并；多次失效则降权淘汰。
当新执行结果与历史经验不一致时，Agent 需能修正、补充或合并已有经验；对多次被证明错误或失效的经验，需降低优先级甚至淘汰。
展开 ▾
REQ 8.6

成功经验逐步固化复用

多次验证有效的经验沉淀为标准化流程或可复用能力。
对多次执行验证有效、稳定成功的经验，Agent 应逐渐沉淀成更标准化的操作流程或可复用能力，使类似任务后续不再每次从头探索。
展开 ▾
REQ 8.7

失败经验形成约束

记住导致异常的操作/出错的判断/不可执行的条件。
不仅要记住「怎么做成功」，还要记住哪些操作曾导致异常、哪些判断曾出错、哪些条件下不能执行，从而让 Agent 后续主动规避相同错误。
展开 ▾
REQ 8.8

迭代结果可验证可追溯

每次新增/修改/淘汰经验保留来源，经人批准避免越改越差。
Agent 每次新增、修改或淘汰经验都需保留来源和依据，并通过任务结果验证修改是否真的有效，任何修改都需要有人批准，避免 Agent「自己越改越差」。
展开 ▾
SOLUTION · MINDMEMOS

MindMemOS 能力对照

MindMemOS 提供了经验沉淀与自迭代的底层能力，但仍需补充运维专属语义与决策机制。绿色为已提供，橙色为仍需补充。

需求
MindMemOS 可以提供
仍然缺乏
REQ 8.1
经验自动识别与沉淀
提供支持从对话和执行轨迹自动抽取记忆，通过 Schema Add 按实体/属性/事件结构化存储，保留 Task、Session、Agent、时间等上下文。
缺乏缺少运维专属经验定义，无法天然识别检查方法、操作顺序、关键参数、判断依据、异常处理、成功/失败原因，需补充运维经验 Schema 和轨迹解析逻辑。
REQ 8.2
经验按场景准确召回
提供支持语义检索、Schema Search、Agentic Search、Rerank，可按实体/属性/时间/关系召回相关历史经验，而非仅关键词匹配。
缺乏缺少运维场景相似度定义，需明确业务类型、操作对象、SOP Step、工具、环境状态如何共同决定「是否相似变更」。
REQ 8.3
经验真正参与当前决策
提供可在 Agent 执行前检索相关经验，并通过 Memory Injection 注入当前上下文，供 Planner 和 Agent 使用。
缺乏缺少经验驱动决策机制，MindMemOS 负责「找出经验」，但不保证 Agent 据此调整计划、工具选择、风险判断和核验方式，需在 Agent Harness 中补充。
REQ 8.4
经验有效性验证
提供支持显式与隐式 Feedback，可根据后续反馈对 Memory 进行新增、修改和删除。
缺乏缺少当前业务事实校验，无法自行判断历史经验是否仍符合当前 SOP、生产环境和真实执行状态，需增加经验使用前的验证机制。
REQ 8.5
经验持续更新与纠错
提供支持 Memory Update / Archive / Delete，并通过 Dreaming 对重复、冲突和相关经验进行整理和合并。
缺乏缺少经验质量管理规则，如连续失败多少次需降权、SOP 更新后哪些经验失效、冲突经验如何处理，需业务侧定义。
REQ 8.6
成功经验逐步固化复用
提供支持 Skill Evolution，可汇总多条真实执行轨迹自动总结经验，并基于经验修改 Skill、生成新版本。
缺乏缺少经验晋升标准，需定义什么经验只保留为 Memory、什么经验经多次验证后可升级为稳定 Skill。
REQ 8.7
失败经验形成约束
提供支持为轨迹记录 Score，Skill Evolution 可利用高分和低分轨迹调整 Skill；失败经验也可通过 Feedback 长期保存。
缺乏缺少运维风险语义，需把失败经验整理成「禁止条件、前置检查、风险条件、异常停止、回退条件」等可执行约束。
REQ 8.8
迭代结果可验证可追溯
提供支持 Skill Version、History、Diff、Rollback，保留轨迹到新版本的演化关系，新版本也可先以 Draft 形式存在。
缺乏缺少业务效果验证闭环，需增加新旧版本测评、真实变更验证和发布 Gate，确保 Skill 更新后真的变好而非越改越差。
